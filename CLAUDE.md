# Rapid Oven Cleaning CRM

Single-file CRM (`index.html`) for Rapid Oven Cleaning (Sydney oven/BBQ cleaning business, run by Aaron). No build step — it's one static HTML file with inline CSS/JS, deployed via **GitHub Pages** straight from `main` at https://kingazzal69.github.io/rapid-oven-crm/

## Deploy workflow

- Edit `index.html` directly, no build/bundler.
- Commit, then push to `origin main` — GitHub Pages redeploys automatically (usually 1-2 min).
- **Git identity:** no global git config is set on the dev machine. Commit with explicit env vars matching the existing author on this repo's history:
  `GIT_AUTHOR_NAME="Aaron" GIT_AUTHOR_EMAIL="accounts@rapidovencleaning.com" GIT_COMMITTER_NAME="Aaron" GIT_COMMITTER_EMAIL="accounts@rapidovencleaning.com" git commit -m "..."`
- **Deploy lag gotcha:** after pushing, the live site can take a minute+ to actually rebuild. If you write data (e.g. to Supabase) that depends on a just-pushed code change being live, verify the deploy landed first (poll the page for a string unique to the new code) — don't assume push = instantly live. This bit us once: a bulk data import ran before a Pipeline-filtering code fix had actually deployed, and briefly showed unfiltered data on the live site.
- Established convention with Aaron: commit when asked to "commit", but only `git push` when he explicitly says "push" / "make it live" / "push to live" — don't push on your own initiative for functional index.html changes. (Pure docs files like this one, with zero effect on the live rendered page, are fine to push directly.)

## Data layer — Supabase

- Project: `haarvltpfcbixqbwkxpl` (`https://haarvltpfcbixqbwkxpl.supabase.co`). URL + anon key are embedded directly in `index.html` (near the top of the `<script>` block). **Row Level Security is ON (since 4 Oct 2026)** on `leads`/`projects`/`todos`/`config`/`job_count_daily`: only the shared CRM login, signed in *with* its authenticator code (`aal2`), can read or write them. The anon key alone now gets `[]` (and writes fail), so you can't inspect data with it via REST any more. Use the Supabase SQL Editor, or n8n's service_role credentials. `staff_earnings` and `crm_data` are locked (RLS on, no policies). n8n (Lead Sync, Job Count Tracker) uses the service_role key, which bypasses RLS.
- **Tables:** `leads`, `projects`, `todos`, `config` (all shape `{id text, data jsonb, updated_at}` — the CRM reads/writes via `.select('*')` / `.upsert({id,data,updated_at},{onConflict:'id'})`), plus `staff_earnings` (no longer used: the Square tab was removed and its n8n workflow is switched off).
- **Supabase caps any single select at 1000 rows.** `leads` now has 12k+ rows (see ServiceM8 import below), so the app pages through with `.range()` — see `fetchPaged()` / `fetchActiveLeadRows()` / `fetchArchivedLeadRows()` in `index.html`. If you add a new bulk-reading query anywhere, don't use a plain unbounded `.select('*')` — it will silently truncate at 1000 and can empty the Pipeline board (this happened once, see git history "Fix pipeline emptied by 1000-row Supabase select cap").

## Sign-in gate

- The whole CRM sits behind one shared login (password, then a 6-digit authenticator code, once per device). The session lives in localStorage, so devices stay signed in until someone signs out. `init()` (all data loading) only runs after the session reaches `aal2`; see `bootAuth()` / `unlock()` in `index.html`.
- The gate never sets up an authenticator code by itself. With no verified code on the login it shows "ask Aaron"; a code is set up deliberately by opening the CRM with `#setup-2fa` on the end of the address.
- Account button: "Sign out of this device" (`signOut({scope:'local'})` + reload) and "Sign out all other devices" (`scope:'others'`). Never use the default global sign-out: the login is shared, so it would sign out every staff phone.
- Writes go through `upsertRow`/`deleteRow`, which refuse to write until the initial load succeeded (`loadOk`), so a failed or signed-out load can never overwrite real data with defaults. No demo/seed data exists any more.
- Row ids are rendered into inline `onclick="…('id')"` handlers, so rows whose id isn't `[A-Za-z0-9_-]` are skipped on load (`SAFE_ID`).

## Pipeline / leads data model

- A lead is `{id, name, phone, email, service, source, stage, value, suburb, address, notes, createdAt, followUp, jobDate, jobTime, assignedTo, history[], archived?, d1?, d2?, d3?, trackedAt?}`.
- `stage` is one of: `new`, `contacted`, `deadlead`, `followup`, `quoted`, `won`, `lost` (see `STAGES` array in `index.html`). `won`/`lost`/`deadlead` are terminal (see `TERMINAL_STAGES`) and excluded from the pipeline's happy-path advance arrow (see `STAGE_FLOW`) — `deadlead` ("Lost Lead") is for leads that went cold after contact, distinct from `lost` ("Closed — Lost") which is for quotes that didn't convert.
- `d1`/`d2`/`d3` are plain booleans toggled by the "D1"/"D2"/"D3" checkboxes in the tracking row at the bottom of each Pipeline card (see `toggleFlag()`) — manual tick-off checkboxes for Aaron's own workflow (day-1/2/3 follow-up done). Ticking D1 on a New lead moves it to Contacted; ticking D2 on a New/Contacted lead moves it to Follow Up (`FLAG_STAGE`); forward only, unticking never moves it back. Each tick also stamps `d1At`/`d2At`/`d3At` (ms, removed on untick; shown in the pill's tooltip). Today › Follow Up lists leads with D1 ticked in the last 3 days (`d1At`, falling back to `trackedAt` for ticks made before d1At existed) and no D2. No stat/report currently reads them. (A `messaged` field/checkbox existed briefly but was removed — some older lead rows in Supabase may still carry a stray `messaged` key; harmless, just unused.)
- `trackedAt` is a timestamp (ms) set by `toggleFlag()` any time a D1/D2/D3 box is ticked — shown as "Updated {date, time}" under the tracking row (see `fmtDT()`) so Aaron can see at a glance when a lead's follow-up checkboxes were last touched.
- **`archived: true`** marks a lead as historical/reference-only (currently: ~11.7k rows bulk-imported from ServiceM8's full job history, dated 2020–2026). Archived leads are deliberately excluded from the live Pipeline board, stat tiles, and Map (see `activeLeads()` helper) — they only show up in the Clients Database table (lazy-loaded on that tab). (The CSV Export button was removed; a nightly n8n backup replaces it.) **Keep this separation if you touch board/stats/map rendering** — Aaron was very explicit that historical bulk data must never pollute the live working pipeline.
- **Source tags are colour-coded** by `leadSource()`/`srcChip()`: synced leads all have `source:"ServiceM8"`, so the real channel is read from `service` ("… new lead (Meta)", "[Missed Call/Text] - …"), falling back to `source`. Display only, never saved. Colours in `SRC_COLORS`; unknown sources get a stable colour from `SRC_EXTRA`; ServiceM8/Zapier/Other stay grey.
- Names sync in from ServiceM8 as `"Last, First"` (e.g. `"Bowman, Trudy"`), while manual/seed leads are `"First Last"`. Use the `firstNameOf()` helper (handles both) rather than a naive `split(' ')[0]` anywhere you need a first name — this was a real bug (SMS templates were greeting people by surname).

## SMS follow-up templates

- `tpls` array (near the top of the `<script>` block) provides default SMS templates with `{name}`/`{service}`/`{value}`/`{suburb}`/`{address}`/`{jobwhen}` placeholders. Supabase `config.data.tpls` overrides the defaults when present. Templates can be edited in the lead modal's Follow-up section. (Bulk SMS has its own separate template list — see below.)
- `pickTplForStage(stage)` maps pipeline stage → template index for the **quick-SMS 💬 button** that sits on every Pipeline card (opens the phone's native SMS app via an `sms:` URI with the message pre-filled). Keep this mapping in sync if templates are added/reordered.
- Business voice: texts are signed from "Aaron" at Rapid Oven Cleaning (changed from Brenna, 26 Oct 2026) — casual, short, no corporate tone.
- **Bulk SMS** (Clients tab: the sticky "N selected · Clear · Text them" bar, plus a Bulk SMS button at the right end of the desktop toolbar): texts only the ticked clients. "Select all N" ticks every client matching the filters across all pages; the single "Date range" button fills the hidden `fFrom`/`fTo` inputs. Ticks persist across pages/filters in `sessionStorage` (`selectedClientIds`). Flow: compose → server **review** → send once → result on screen + Telegram summary. There is no separate bulk SMS sign-in: it uses the CRM's own sign-in (see "Sign-in gate" below). Full setup/testing/rollback: `supabase/functions/bulk-sms/SETUP.md`.
- The server side (`supabase/functions/bulk-sms/index.ts`) is the authority: it requires the `SMS_ALLOWED_EMAILS` account *with* two-factor (`aal2`), re-reads numbers from `leads`, merges duplicates per canonical `614XXXXXXXX` number, drops opted-out numbers (`bulk_sms_suppressions`), and claims each batch atomically so it can never send twice. Its `personalise()` must stay identical to `personaliseSmsText()`/`firstNameOf()` in `index.html` (a test checks this).
- Bulk templates live in `bulk_sms_templates` (seeded once from `tpls`), separate from quick-SMS `tpls`/`config` — bulk edits must never write to `config`. Bulk SMS tables (`supabase/migrations/0001_bulk_sms.sql`) have RLS on with no policies, so anon/authenticated get nothing; only the function (service role) can reach them. Bulk templates must use plain characters — MobileMessage drops —, ’ etc.
- Sending goes via the n8n workflow **"Rapid Oven – Bulk SMS (MobileMessage)"** (id `aRcdRb22RQCmPK5C`, source `n8n/rapid-oven-bulk-sms.workflow.ts`), separate from every other workflow. MobileMessage/Telegram credentials live in n8n only, never in the page.
- Tests (no network, no real SMS): `node supabase/functions/bulk-sms/test/run.mjs`, `.../workflow.mjs`, and `.../browser.mjs` (needs Playwright).

## Integrations this CRM depends on (external, not in this repo)

- **n8n → Supabase sync** (self-hosted n8n on a Hostinger VPS): pulls ServiceM8 jobs and upserts them into the `leads` table on a schedule, keyed `sm8_<job_uuid>`. This is what keeps New Leads etc. flowing in live. Full architecture/history is in Aaron's Claude memory (`n8n-servicem8-crm-sync`), not in this repo.
- **ServiceM8 Job Count Tracker** (n8n workflow `Sli5JgRHFMOGTgCJ`): runs **every hour** (changed from every 5 hours on 29 Sep 2026; the page's "syncs every hour" label should match). Its ServiceM8/Supabase request steps retry up to 5 times, 5s apart — added after a single ServiceM8 504 timeout on one of its ~215 per-job lookups failed a whole run. Writes one `job_count_daily` row per day (`date`, `quotes`, `work_orders`, `total`, `jobs[]`, `updated_at`) that feeds the Job Count tab. Each `jobs[]` entry is `{time, status, customer, description}`; since 28 Sep 2026 the workflow's "Fetch ServiceM8 Staff" step also adds `staff` (the ServiceM8 staff member's full name, empty = unassigned). When `staff` is present the tab shows two per-staff views: the **Staff Schedule** cards (day strip + one card per staff member, every job at its real time; `renderJcSchedule()`) and, when a Daily Breakdown day is expanded, the **slot grid** (column per staff, rows = the 7/9/11/1/3/4:30 slots the Telegram Schedule Builder bot uses, ‹ › buttons to scroll across staff; `jcStaffGrid()`). Without `staff` it falls back to the plain list. Free slots = each person's daily capacity minus jobs booked, from `JC_STAFF_CAP` (Aaron 6, Jackson 3, Paras 4, Kapil 5, Bhuwan 5, keyed by first name) — those staff always show, even with no bookings; free boxes go on their earliest open standard slots. Weekly roster `JC_ROSTER` (by weekday, first names): Mon & Wed Aaron/Jackson/Bhuwan; Tue/Thu/Fri everyone; Sat & Sun Aaron/Kapil/Paras. Staff not rostered show greyed as "Off" (listed last, no free slots; any job they do have still shows). Day-level totals (day strip, day title) are **overall**: all jobs booked that day (unassigned and off-staff included) against the rostered staff's combined capacity (`jcDayCap()`: 14 Mon/Wed, 23 Tue/Thu/Fri, 15 Sat/Sun), e.g. "16/23 booked · 7 free" — not the sum of each person's free slots (Aaron asked for this). Job times are never moved. Placeholder-looking jobs (e.g. "Name #1789…" at 1am) are real jobs — Aaron asked to keep them.
  - Since 15 Oct 2026: entries also carry `phone` + `leadId` (for Today › Reviews). Statuses counted are Quote, Work Order **and Completed** (Completed counts under `work_orders`, so Q + WO = total; the CRM labels it "Done" via `jobKind()`). Before this, jobs vanished from the day once staff completed them. Jobs with no `sm8_` lead (old quotes booked in later: Lead Sync only sees jobs *created* in the last 2 days) or no phone get name + number straight from ServiceM8 (Find Jobs Missing Contact → Fetch Missing Companies/Contacts). Booked Quote/Work Order jobs with no lead are added as New `sm8_` leads (Build/Upsert Missing Leads, `ignore-duplicates`, so existing leads are never overwritten). Lead Sync's `pickContact()` skips inactive contacts and prefers one with a number.
- **Nightly Review Texts** (n8n workflow `ClpMRFu73duAlXQP`, source `n8n/rapid-oven-nightly-reviews.workflow.ts`, live since 17 Oct 2026): 7:10pm Sydney daily, just after the tracker's 7pm run. Texts every job in today's `job_count_daily` row (Quote, Work Order, Completed) the day's Review 1/2/3 text via MobileMessage as `OvenClean`, with `shorten_urls:'auto'` (the g.page link becomes a 22-char tracked `addr.au` link, counted after shortening). Skips: no mobile, `bulk_sms_suppressions`, already texted today (`reviewSentAt`, e.g. from Today › Reviews), texted in the last 180 days (by number, across leads), duplicate numbers; MobileMessage itself blocks its unsubscribe list (`blocked`). Any failed lookup or job data over 2h old = nothing sent. Accepted texts stamp `reviewSentAt` + a history line on the lead (full-row upsert); Telegram summary to Aaron. `DRY_RUN` const at the top of "Build Review Texts". Its `REVIEW_DEFAULTS` must match `REVIEW_TPLS` in `index.html` (`config` has no saved `tpls`, so both use the defaults); review texts stay at or under 160 plain characters = 1 SMS credit. No `{optout}` tag (Aaron's choice, 17 Oct).
- **Square → staff_earnings sync**: n8n workflow `KjfjAwmAxjVbuI2T`, switched **off** (Oct 2026); the Square tab was removed earlier. `staff_earnings` data is kept but locked.
- **ServiceM8 → CRM one-time historical backfill**: already done (Sept 2026) — ~11.7k historical jobs imported as `archived:true` rows with id prefix `sm8hist_<job_uuid>` (distinct from the live sync's `sm8_` prefix, specifically so it's easy to bulk-identify/remove if ever needed and can't collide with the live incremental sync).

## Things to be careful with

- This is Aaron's real, daily-used business tool — every change here is effectively "in production" the moment it's pushed. No staging environment.
- Files outside a Claude session's own project folder render as a **static snapshot** in some sandboxed browser-preview tools (no live JS) — don't assume a preview screenshot means the code actually ran; verify logic by careful reading + a real deploy check when a true headless browser isn't available.
- No test suite, no linter, no build — verify changes by reading the diff carefully (brace/paren balance is a cheap sanity check for template-literal-heavy edits) and, where possible, exercising the actual live site (it needs the shared login now) or the Supabase SQL Editor.
